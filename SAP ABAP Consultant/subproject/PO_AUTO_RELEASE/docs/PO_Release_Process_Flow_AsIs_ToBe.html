Process Flow — Release Purchase Order

AS-IS (manual) vs TO-BE (otomatis via ZMMI_PO_RELEASE_PHASE2). Sistem TRS / ECC 6.0. Sumber: thread email "Purchasing Restructure" + implementasi Sprint 1–2.

AS-IS — Manual

Kondisi sekarang, semua release manual
Buyer buat PO — ME21N
PO ter-block, FRGRL = 'X'
Masuk antrian release
Semua nilai PO, tanpa filter
Approver cek satu per satu
ME28 / ME29N, tanpa notifikasi
Evaluasi manual
Nilai, vendor, harga dinilai sendiri
Release / tolak manual
GM & lead jadi bottleneck
Masalah: PO kecil ikut antre, GM overload, tak ada penanda risiko (vendor/harga), tak ada reminder, proses lambat.

TO-BE — Otomatis

ZMMI_PO_RELEASE_PHASE2 (background job)
Buyer buat PO — ME21N
PO ter-block, FRGRL = 'X'
Background job jalanLIVE
Terjadwal, baca PO pending
Hitung USD & tentukan tierLIVE
Kurs tgl PO → mapping ZMAP_TYPE
T0 < $500
AUTO release (BAPI)
T1 $500–5k
Route Purch. Lead
T2 > $5k
Route GM Purch.
Exception flagging (T1/T2)LIVE
Vendor/Material baru, HrgNaik, Stale, Svc/Capex
Email notif ke approverRENCANA
Blocker: SMTP/SCOT belum di-setup
Approver review & release
Flag terlihat → ME29N (T1/T2)
LIVE sudah jalan di sandbox TRS RENCANA belum / diblokir dependency Approval tetap di dalam SAP — email hanya reminder
Belum diterapkan di TO-BE: email notifikasi (blocker SMTP), aksi hilir exception, data GM asli, keputusan boundary tier, konstanta ke ZMAP_TYPE, optimasi performa lookup, transport ke DEV/QAS/PRD, penjadwalan job SM36. Semua masih di $TMP / sandbox TRS.
